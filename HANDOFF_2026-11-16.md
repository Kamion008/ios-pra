# HANDOFF 2026-11-16 — iOS-on-PRA-LX1 (hi6250/Kirin 655)

## 1. GOAL AND CURRENT STATE

Goal: boot the iPhone X iOS 16.7.16 userland on a Huawei PRA-LX1 to a visible
iOS screen — the lock screen first (donor-proven, CPU rendering), the Hello
screen later (needs a real GPU). Works today: XNU boots, root mounts RW,
launchd runs daemons, SpringBoard + backboardd exec, the render pipeline
created a 1080×1920 IOSurface and presented 7 swaps, the touch IC answers on
I2C. Single blocker: after SpringBoard's first surface call, EVERY thread of
SpringBoard and backboardd parks inside libsystem_kernel syscall stubs
(majority trap -13 = task_dyld_process_info_notify_get) for the rest of the
boot with zero further presents — cause unknown, because the sampler only
dumps user PCs. Kernel-side visibility is the missing tool (0173, half-written).

## 3. REFUTED THEORIES (do not retry)

- CMD18 multi-block reads, any stop variant: auto-CMD12 (0162-era boot),
  manual CMD12 (emmcmulti=2 — VOID experiment: that kernel never shipped,
  see the CI-skip fact), CMD23 (emmcmulti=1 boot, flood seen, ring lost).
  All wedge the card until power cycle. Per-sector CMD17 is the only working
  IO path. Evidence: WORKLOG sections 12-14, the CI logs, ring21≡ring20.
- fLock/vsync-notify deadlock in AppleCLCD: notify() is asynchronous —
  patch 0046's `IOMobileFramebufferUserClient::notify` ends with
  `sendAsyncResult64WithOptions(..., kIOUserNotifyOptionCanDrop)` (send and
  return). Cannot block on the client. Refuted by code read.
- mach_vm_deallocate / VM-map-lock contention: off-by-one stub decode — the
  saved pc of a syscall-blocked thread is the RET *after* the SVC, so the
  in-flight trap is the one whose MOVN/SVC immediately precede it (-13), not
  the -12 whose RET the pc sits on. Also two processes cannot share one VM
  map lock. Refuted.
- "GPU absence blocks the lock screen": the donor reached the lock screen
  CPU-rendered (DREAMLTE:91). Setup (purplebuddy) itself does need a GPU
  device to render (ring24/27: main thread in MIL 54/79 samples) — which is
  why the SetupDone bypass exists. The GPU work (0171) is still needed for
  real Hello/acceleration later, but not for the lock screen.
- "0165 halves boot IO": the churners are EPERM'd BEFORE their image is read
  — each retry is IO-trivial; the 615× counts are launchd's ~10 s
  ThrottleInterval over the boot. The churn is CPU noise, not IO cost.
- 0148/0162/0163 "shipped and fixed the wedge": they never reached a kernel
  (CI silent skip). Never compare pre-0164 flood conclusions against shipped
  kernels.
- .symbols offline symbol lookup: BROKEN for this extraction (header parse
  at 0x4000 yields garbage: lsListOffset=0x84d7130000a980). Image-NAME
  resolution via the main cache image list (img() in work/sym29.py) is
  verified working. Do not trust symbol-level output from sym*.py.

## 4. OPEN HYPOTHESES (ranked)

- H1 (0.45): a common kernel-side wait. All stuck threads are IN the kernel
  (saved pc = syscall return); the -13 trap touches user memory (copyin/
  copyout of the dyld notify ports) and ipc port operations — any of those
  can fault/wait on a shared resource (the DSC pager, the root-file IO, an
  ipc-space lock). Predicts: kernel backtraces of the stuck threads show a
  common frame (pager/vnode/lock). Falsifies if kernel stacks differ and
  look like unrelated idle waits. Cheapest test: the 0173 sampler kernel-bt +
  wait-event hunk — ONE boot.
- H2 (0.3): the -13 trap itself deadlocks kernel-side (g_dyldinfo_mtx /
  itk_lock / an ipc-space lock held by a thread that never finishes).
  Predicts: a holder thread visible in the kernel stacks; possibly in EVERY
  process that registered a dyld notifier. Test: same 0173 boot; if stacks
  are unclear, add a rate-limited print inside the trap when it exceeds 10 s.
- H3 (0.15): IO-bound grind — the DSC page-ins at ~550 KiB/s need hours and
  the threads would eventually proceed. ALREADY WEAKENED: 17/19 identical
  pcs over ~3 h means no visible progress in the sampled window. Only
  survives if the progress happens in bursts between samples.
- H4 (0.1): a missing root tweak the donor had ("SpringBoard first-boot
  tweaks"; their tools/dreamlte/finish-iosroot.sh referenced in
  DREAMLETE_PROGRESS.md:86 is NOT in this repo — content UNKNOWN). Test:
  obtain the donor recipe and diff the staged roots.

## 5. KNOWN-BAD OR UNCERTAIN TOOLING

- .symbols lookup: broken (see refuted list). Image-name lookup works.
- Slide: ALWAYS take it from the sampler's own `SMP <proc>[pid] slide 0x…`
  line (per-process; ring29: all three procs 0x2e834000, consistent).
- Shared-cache byte reads: the MAIN cache file holds only the header region
  (one mapping, 368 KB). Code bytes live in the numbered subcaches, each
  with its own dyld_v1 header (mappingOffset/count at +16/+20). Correct
  read: find the covering subcache, file offset = mapping.fileOffset +
  (vm − mapping.vm). The first extraction grabbed only .01-.04 — copy ALL
  (42 files, 3.2 GB). The main-file read at (vm − image-la) produces GARBAGE
  that looks like data (0x9b183000) — that failure mode wasted an hour.
- Trap decode off-by-one: saved pc = the RET AFTER the SVC; the in-flight
  trap is the stub whose MOVN/SVC immediately precede the pc. Verify each
  pc against osfmk/mach/syscall_sw.h order (-10 allocate, -11 purgable,
  -12 deallocate, -13 notify-get, -14 protect …).
- git 2.56 locally skip-detects already-applied patches with rc=0 → local
  `git apply --check` proves nothing. GNU patch 2.8.1 fails on 0058/0061/
  0071/0118 (git-only diff forms) and mis-parses the fabricated
  `index 0000000..1111111` lines (treats them as file-creation markers).
  Reliable recipe (touch agent, CI run 43762967094): run the three stage
  .sh scripts from xnu/patches, then `git apply` ALL patches in order
  (atomic, zero skips), then GNU `patch -p1 --fuzz=0 --dry-run` on
  index-stripped diffs as the per-patch oracle.
- The pralog ring is a 4 MiB circular buffer: a dump shows only the LAST
  4 MiB, wrapped. Wedge/panic boots lose evidence (the flusher shares
  pra_emmc_lock; 0166 improved this; the ring26 panic flush still failed
  with "panic flush failed 16" — see work/ring26-panic-screen.txt).
- The stats lines are deterministic per workload phase: identical last-line
  values across boots (ring28/29) do NOT mean stale rings — compare line
  COUNTS and first-vs-last positions.
- /tmp is volatile (the PC restarted mid-session today; ring26/27 txt and
  three scratch trees died). Durable copies: work/ and research/pra-artifacts/.
- apfs-fuse mounts work unprivileged for ro; fusermount -u may fail with
  permission denied — leave mounted or umount.
