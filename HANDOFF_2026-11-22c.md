HANDOFF - PRA Touch, after T21c (2026-11-22c, written 22:1x UTC)
SUPERSEDES HANDOFF_2026-11-22b.md. Self-contained: read this plus AGENTS.md.

STATUS: **TOUCH WORKED ON THE PHONE FOR THE FIRST TIME.** In the T21c boot
(image dd8bb8c5, kernel 0198+0199+0200, flashed 19:32:23 UTC) the user got
into iOS and touch responded - intermittently, "sometimes yes sometimes no,
I think according to the power button", and they never pressed the physical
power button at any point. The blocker is therefore NOT the digitizer event
shape: it is a WAKE / DISPLAY-STATE gate. backboardd's own persisted unified
log says `digitizerEnabled: NO` and `display: off` in the winning
`BKSHIDUISensorMode`, with the reason `idle timer` - the normal sleep mode -
and a wake event flips it to the awake mode, which re-enables the digitizer
stream. Our synthetic POWER key (0198/0199, one pair at +900 s then every
30 s) was acting as that wake.

THE PROJECT
Goal: run the unmodified iPhone X iOS 16.7.16 userland on a Huawei PRA-LX1
(Kirin 655 / hi6250). Path: Android boot image -> EL1 loader (shim/pra) ->
ported XNU 8796.141.3 -> the iOS root from the donor ios-galaxy-s8 (SWEET /
A5XELTE). Userland stays unmodified; every change is kernel-side. The phone
boots to the iOS lock screen, the display is live at 1080x1920, and as of
T21c it can be unlocked and used with touch.

WHAT IS PROVEN (unchanged unless noted)
- T13-T19: IC in app mode (32-byte descriptor, max_input=254), 10 ms poll,
  579 reports over 840 s, 2.8% read errors, in-bounds coordinates; the 0172
  probe is the ONLY place `pratouch` is parsed, so every touch boot must pass
  `pratouch=1 pratouchreset=1`.
- T16/T20: SweetHIDTouch builds a 236-byte digitizer collection per contact,
  enqueues it into a 16 KiB IODataQueue, backboardd maps and ARMS both
  queues (SweetHIDTouch and SweetHIDButtons) and DRAINS them (641 events,
  9.2x capacity, drop=0, head==tail at every sample).
- T20: a synthetic 3x unlock swipe was delivered 3/3 exactly as designed and
  nothing accepted it (the UI was inert because the digitizer was disabled,
  not because the event was wrong - see T21c).
- T21a (ring63, patch 0198, `prapowerkey=300`): the consumer key path works -
  `powerkey 1 down ... usage 0x30`, `SWEET HID: key 0x30 down (1 clients)`,
  `event size=60 sender=0x100000127`, and the BUTTONS queue read
  `enq=2 drop=0 type=3 head=128 tail=128` = 2*(60+4) = 128 = 64*2, drained.
  The press fired ~5 min after power-on, before any UI could consume it.
- T21c: TOUCH + UNLOCK WORK (user report, intermittent). First boot in 21
  where a human confirmed the UI consumed input.
- The queue accounting is closed: 4 B `IODataQueueEntry` header per entry
  (IODataQueueShared.h:79), so a key entry advances `head` by 64 B and a
  digitizer entry by 240 B.

THE NEW EVIDENCE (the thing that changed everything)
`work/userland-logs-2026-11-22.md` - the iOS userland's OWN persisted log,
read off the eMMC root. The root is journaled case-sensitive HFSX and TWRP
has NO HFS+ driver, so it was read block-wise (extents resolved through the
extents-overflow B-tree) and the `.tracev3` archives carved. Findings:
- `<BKIOHIDService: ... serviceStatus: matched; name:SweetHIDTouch
  id:0x10000012a primaryUsagePage:0xd usage:0x4 transport:SPU ...; builtin;
  authenticated: YES` - our digitizer service IS matched by backboardd.
- `<BKDigitizerStreamClient: ... pid: 26 SpringBoard system-gestures ...>` -
  SpringBoard's gesture stream client EXISTS. The consumer was never missing.
- `reason: SB + backlight-off + pocketTouches; ... digitizerEnabled: NO;
  display: off` (and elsewhere `digitizerWake: YES; display: on`).
- `edDigitizerRect:{{0,0},{1,1}}` - REFUTED as a bug: that is
  `normalizedDigitizerRect` in 0..1 display space, i.e. correct full
  coverage. Do NOT publish a pixel rect.
- `events:0` - NOT a drop counter; it is the service-description snapshot
  taken on the `matched` transition.
- The host-state contract our service never honours: `MultitouchHostStateKeys`
  (`ScreenOn`, `DigitizerSurfaceCovered`, `PocketTouchesExpected`,
  `WakeOnTapEnabled`, ...), `setElementValue:forUsagePage:usage:`,
  `NeedsHostState`, `HostStateNotification`, `send tapToWake to %@`.

`work/digitizer-gate-2026-11-22.md` - the full decode of those records plus
the patch plan: 0201 instruments the three interfaces, 0202 publishes the
host-state contract, 0203 fixes display-power reporting (0203 LAST: it can
blank the panel).

THE PATCH STACK (all landed, commits on master)
- 0198 `prapowerkey=N`: a consumer POWER (0x30) pair N s after
  `SweetHIDButtons::start()`, then a volume-up (0xE9) pair 120 s later.
- 0199 `prakeyevery=M`: repeat mode, one pair every M s alternating power /
  volume-up, up to SWEET_KEY_MAX_PAIRS = 240 (python3: 240*30 = 7200 s = 2 h).
- 0200: the arm report fires at `prapowerkey` seconds instead of +30 s,
  because +30 s is inside the window where IOLog never reaches the ring
  (`grep -c 'arm secs'` on ring63 = 0). `armed=` now means allocated AND
  err==0. NOTE: 0200's own patch header says the report timer "is armed
  first" - that is WRONG (fKey is armed first at post0200:463, fArm at :482
  with the same timeout), so which of the two lines prints first is not
  guaranteed. Do not rely on the order.
- 0201 `pra-hid-hoststate-instrumentation`: logs every RequestPowerChange
  with the raw argument (even when keep_on swallows it), every notification
  registration, `setElementValue`/`setProperties` pushes from backboardd,
  plus the ONE behaviour change: our digitizer events now carry
  `kIOHIDEventFieldDigitizerIsDisplayIntegrated`. 81 added / 2 removed.
  Its marker assert broke a green build (CI 45074770951) because the format
  string is `SWEET HID: %s setElementValue ...`; fixed in 7f20894
  (assert on `setElementValue page 0x%x`).

CAUSALITY - NOT YET SEPARATED (the main open question)
Touch working in T21c is consistent with, but does not prove, "the synthetic
POWER press wakes the digitizer". Alternatives: the volume-up pair, elapsed
time / SpringBoard finishing its bring-up, or a combination. The user's
report (intermittent, tracking the power button) favours the press, and the
log's `idle timer` reason explains why it would revert. DECIDE WITH:
1. ring64 (TWRP pull): press timestamps (30 s spacing) vs the first
   `SWEET HID: touch` transitions and the `queue stats` deltas around them.
2. The next tracev3 harvest: does `digitizerEnabled` flip to YES after a
   press and back to NO on the idle timer? Is there a `send tapToWake to` or
   `didn't see a previous touch down` (the route log) line after a press?
   Grep keys: `digitizerEnabled`, `digitizerWake`, `backlight-off`,
   `BKDigitizerStreamClient`, `tapToWake`, `digitizer:%llX - display:`.

THE WORKING WORKAROUND (do not break it)
A boot with `prapowerkey=900 prakeyevery=30` re-enables the digitizer within
30 s of the first press and touches work intermittently afterwards. Until
0202/0203 land, ANY touch experiment must include those two args, or it will
look exactly like every pre-T21 boot ("nothing happens").
