## 4. OPEN HYPOTHESES (ranked, with falsifiers)

- H1: the pra_emmc_lock wedge. The waiters block on the mutex while the
  flusher keeps acquiring it every tick — the lock is NOT permanently
  held — so the candidates are: (a) a lost wakeup, (b) UNFAIR STARVATION
  (XNU mutexes are not handoff-ordered; a holder that re-takes the lock
  every tick can beat the woken waiters forever — no code bug needed),
  (c) corrupted lock state. 0176's telemetry must DISCRIMINATE: when the
  contention timer (>10 s) fires, print the mutex's STATE WORD (owner +
  waiter flags), the waiter thread pointers, and the flusher's duty cycle
  (its lock-acquire count per tick). INTERPRETATION: starvation requires
  the flusher to hold the lock ALMOST CONTINUOUSLY (a near-100% duty
  cycle) — if it releases and sleeps between ticks, a woken waiter gets a
  clear window. So LOW duty cycle + hours-long wait = evidence AGAINST
  starvation, pointing to a lost wakeup or bad lock state; high duty cycle
  = starvation/hold-across-sleep; "waiters flagged, no owner" = lost
  wakeup; garbage state = corruption. Each names a different fix.
- H2: the clock is FROZEN vs UNSET vs NEVER-REDRAWN — three different
  bugs with cheap discriminators. 4:08 PM is 488 s after the 1969-12-31
  16:00 epoch default, and boots take ~6 min + photograph time: if the
  clock = epoch + uptime, "4:08 in every boot" could be a COINCIDENCE of
  photographing at the same uptime. Discriminators: (a) photograph the
  lock screen at two DIFFERENT uptimes in one boot (a minute flip =
  advancing; frozen = not), (b) print clock_get_calendar_microtime next to
  mach_absolute_time in the sampler header (a one-line 0176 addition) and
  read both across samples. Also: the lock screen is static after ~5
  presents — the clock LABEL may simply never redraw (a SpringBoard/
  compositor bug, not gettimeofday). Fix path if it IS the conversion:
  osfmk/kern/clock.c, the ADT timebase 1.92 MHz vs the real CNTFRQ, the
  epoch seed.
- H3 (feature): touch input wiring (CYTT21403 reports -> IOKit HID ->
  SpringBoard) = unlock -> home screen. The power button belongs to the
  same HID family; its GPIO/IRQ needs identification on PRA first.
- H4 (cleanup): the remaining launchd.plist churners — one sudo block
  (mount, plistlib-remove the three jobs, umount, fsck) — un-floods the
  ring and boots get cleaner evidence.
