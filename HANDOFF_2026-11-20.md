WHAT'S NEEDED (next boot T17)
-----------------------------
The remaining rung is backboardd's userland: it drains the queue (with a
valid senderID and correct event bytes) but never routes the digitizer
events to SpringBoard. The candidates, in order:
1. **The userland event loop never runs** — backboardd's HIDEventSystem
   thread (IOHIDEventSystem/IOHIDSystem) that reads the queue and
   dispatches may not be started, or its mach receive (the notification
   port we proved armed) is never serviced.
2. **The senderID correlation fails in userland** — IOHIDEventSystem
   matches the event's senderID against its registry of digitizer
   services; 0x100000126 must match the SweetHIDTouch registry entry,
   and the match code may be failing (e.g. the service's IORegistry
   entry not published with the right HID keys).
3. **SpringBoard's BKSHIDEventRouter never connects** — SpringBoard may
   be running but its connection to backboardd's event router (the
   'esuc' open we proved) may be the wrong client class.
4. **The event payload is dropped by backboardd's parser** — 236 B per
   event serializes but backboardd's IOHIDEvent decode may reject the
   collection/child structure (kIOHIDDigitizerIndex/Identity ranges).

NEXT PROBE OPTIONS:
- (A) Log in the kernel whether the notification mach message is
  actually delivered (the mach_port_set / ipc right check) — but the
  port is in userland, not observable from the kernel.
- (B) The sharper probe: log the **event's kIOHIDDigitizerIndex /
  Identity / field values** that the queue carries (already serialized;
  add them to the 1 s event line) and log whether backboardd's dequeue
  advances head per-event (we see it does). That pins whether the
  serialized payload is structurally valid.
- (C) The userland side: this project has NO visibility into backboardd
  internals from the kernel. The cheapest test of the HIDEventSystem
  route is to make the AKS sel-8 (kIOReturnUnsupported) RETURN SUCCESS
  (the SweetKeyStore default case) — if SpringBoard's touch handling is
  gated on a successful AKS call, the UI may start reacting buysel the
  evidence (one-shot triads, no touch correlation) says it won't.
- (D) The most likely real fix candidate: the senderID correlation.
  SweetHIDTouch publishes itself as a generic IOHIDEventService; a real
  device's digitizer is matched by kIOHIDPrimaryUsagePage/Usage =
  Digitizer/TouchScreen. Verify those properties are set (they are: get
  getPrimaryUsagePage/Usage in SweetHID.cpp return Digitizer/TouchScreen)
  AND that backboardd's IOHIDEventSystem uses the registry entry ID
  (0x100000126) — log the service's registry ID at start to confirm the
  published value.
